# Control Book — Library Catalog

Мини‑проект для изучения FastAPI, SQLAlchemy и подходов к хранению данных.

## Запуск

- Активировать venv и установить зависимости:
```bash
pip install -r requirements.txt
```
- Прописать `DATABASE_URL` в корневом `.env`, пример:
```
DATABASE_URL=postgresql+psycopg2://postgres:YOUR_PASSWORD@localhost:5432/library
```
- Применить миграции:
```bash
alembic upgrade head
```
- Запустить API:
```bash
uvicorn library_catalog.main:app --reload --app-dir src
```
- Swagger: http://127.0.0.1:8000/docs

## Подзадачи 

### 1) Проблемы хранения данных в оперативной памяти
Хранение «в памяти» (списки/словари в процессе приложения):
- Преимущества: максимально просто; мгновенно; не требует внешних сервисов.
- Недостатки:
  - Потеря данных при перезапуске процесса.
  - Нет совместного доступа между несколькими экземплярами приложения.
  - Нет транзакций, блокировок, индексов, целостности.
  - Масштабирование невозможно: каждый процесс хранит свой отдельный набор.

Вывод: годится только для черновых прототипов/тестов.


### 3) Преимущества и недостатки файлового хранения (JSON)
- Плюсы:
  - Прозрачно и просто; данные можно открыть любым редактором.
  - Не требует сервера БД.
- Минусы:
  - Конкурентный доступ сложен (блокировки, гонки, повреждение файла).
  - Нет индексов, сложных запросов, транзакций.
  - Производительность падает с ростом файла.


### 5) Сравнение способов хранения
| Критерий | Память | Файл (JSON) | База данных (PostgreSQL) |
|---|---|---|---|
| Сохранность данных | Нет | Да | Да |
| Совместный доступ | Нет | Ограничен, нужен контроль блокировок | Да |
| Запросы/фильтры | Почти нет | Ручная реализация | Богатые возможности SQL |
| Транзакции | Нет | Нет | Да |
| Масштабирование | Нет | Плохо | Хорошо |
| Сложность | Низкая | Низкая‑средняя | Средняя |

Вывод: для продакшн‑решений — СУБД. JSON подходит для простых офлайн‑сценариев и учебных задач.


### 7) Конкурентный доступ к данным (race conditions)
Проблемы:
- Двойное добавление (нет уникальности), «потерянные обновления», частичная запись.
- Для JSON‑файла: конфликтующая запись из двух процессов может повредить файл.
- Для БД: конкурирующие транзакции, блокировки строк/таблиц.

Стратегии:
- JSON:
  - Файловые блокировки (`portalocker`), атомарная запись (`os.replace`).
  - Версионирование файла (проверять, что не изменился с момента чтения).
- PostgreSQL:
  - Транзакции, индексы уникальности (например, на `book_id`/комбинации полей).
  - Optimistic locking (версия записи/штамп), правильный уровень изоляции.

## Маршруты API (минимум)
- POST `/books/` — создать книгу
- GET `/books/` — список книг с фильтрами (query‑параметры)
- GET `/books/{book_id}` — получить одну книгу
- PATCH `/books/` — частичное обновление по `book_id` (query)
- DELETE `/books/` — удалить по `book_id` (query)
