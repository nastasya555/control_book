# Control Book — Library Catalog

Мини‑проект для изучения FastAPI, SQLAlchemy и подходов к хранению данных.

## Запуск

- Активировать venv и установить зависимости:
```bash
pip install -r requirements.txt
```
- Прописать `DATABASE_URL` в корневом `.env`, пример:
```
DATABASE_URL=postgresql+psycopg2://postgres:YOUR_PASSWORD@localhost:5432/library
```
- Применить миграции:
```bash
alembic upgrade head
```
- Запустить API:
```bash
uvicorn library_catalog.main:app --reload --app-dir src
```
- Swagger: http://127.0.0.1:8000/docs

## Подзадачи 

### 1) Проблемы хранения данных в оперативной памяти

##### Критические недостатки:

**1. Энергозависимость**
- Полная потеря всех данных при:
  - Перезапуске приложения
  - Аварийном завершении процесса
  - Перезагрузке сервера
  - Обновлении версии приложения
- Невозможность восстановления состояния после сбоя

**2. Отсутствие разделяемого доступа**
- Каждый запущенный экземпляр приложения имеет свою изолированную копию данных
- Невозможность организации кластера или горизонтального масштабирования
- Проблемы с балансировкой нагрузки между несколькими инстансами

**3. Отсутствие механизмов обеспечения целостности**
- **Нет транзакций** - невозможность атомарного выполнения группы операций
- **Нет блокировок** - race conditions при конкурентном доступе
- **Нет ACID-свойств** (Atomicity, Consistency, Isolation, Durability)
- **Нет валидации данных** и соблюдения схемы

**4. Ограниченность функциональности**
- **Отсутствие индексов** - линейная сложность поиска O(n)
- **Нет языка запросов** (аналог SQL)
- **Нет механизмов репликации** и резервного копирования
- **Нет встроенной пагинации**, сортировки, агрегаций

**5. Проблемы производительности и масштабирования**
- Ограничение объемом памяти одного процесса
- Фрагментация памяти и сборка мусора при частых операциях
- Невозможность эффективного кэширования на уровне БД
- Отсутствие механизмов шардирования и партиционирования

**6. Безопасность и отказоустойчивость**
- Нет встроенных механизмов аутентификации и авторизации
- Отсутствие аудита операций и логгирования изменений
- Уязвимость к утечкам памяти (memory leaks)


### 3) Преимущества и недостатки файлового хранения (JSON)

##### Преимущества:

**1. Простота использования**
- Человекочитаемый формат - можно открыть любым редактором
- Не требует установки и настройки СУБД
- Быстрый старт для небольших проектов

**2. Универсальность**
- Поддержка во всех языках программирования
- Легкая интеграция с веб-API
- Простота переноса и резервного копирования

##### Недостатки:

**1. Проблемы с конкурентным доступом**
- Сложности при одновременной записи из нескольких процессов
- Риск повреждения данных при сбоях во время записи
- Необходимость ручной реализации блокировок

**2. Ограниченная функциональность**
- Нет индексов - медленный поиск в больших файлах
- Отсутствие транзакций (ACID)
- Нет сложных запросов, JOIN'ов, агрегаций
- Ручная реализация пагинации и сортировки

**3. Производительность**
- Загрузка всего файла в память для работы
- Медленные операции при больших объемах данных
- Нет встроенного кэширования

**4. Масштабируемость**
- Сложность распределения данных между несколькими файлами
- Нет репликации и шардирования
- Ручное управление миграциями схемы данных


### 5) Сравнительный анализ способов хранения данных

## Оперативная память (списки, словари)
**Лучше всего подходит для:**
- Временных вычислений и кэширования
- Быстрых прототипов и тестирования
- Хранения сессионных данных в рамках одного запроса

**Ограничения:**
- Данные теряются при перезапуске приложения
- Нет доступа из нескольких процессов
- Отсутствуют транзакции и блокировки
- Невозможно масштабировать

## Файловое хранение (JSON)
**Лучше всего подходит для:**
- Конфигурационных файлов
- Небольших проектов (до сотен записей)
- Ситуаций, где важна простота просмотра данных

**Ограничения:**
- Медленная работа с большими объемами данных
- Сложности с конкурентным доступом на запись
- Нет индексов и сложных запросов
- Риск повреждения данных при сбоях

## Базы данных (SQL/NoSQL)
**Лучше всего подходит для:**
- Production-приложений
- Систем с большими объемами данных
- Приложений с конкурентным доступом
- Сложных запросов и агрегаций

**Преимущества:**
- Гарантии целостности данных (ACID)
- Поддержка транзакций и блокировок
- Индексы для быстрого поиска
- Масштабируемость и репликация
- Резервное копирование и восстановление

## Рекомендации по выбору

**Для прототипов и тестов:** Оперативная память → Файлы JSON → Встраиваемая БД (SQLite)

**Для небольших проектов:** Файлы JSON → SQLite → Легковесные СУБД

**Для production-систем:** PostgreSQL, MySQL, MongoDB в зависимости от структуры данных

**Для высоконагруженных систем:** Кластерные решения БД + кэширование в оперативной памяти


### 7) Конкурентный доступ к данным (race conditions)
Проблемы:
- Двойное добавление (нет уникальности), «потерянные обновления», частичная запись.
- Для JSON‑файла: конфликтующая запись из двух процессов может повредить файл.
- Для БД: конкурирующие транзакции, блокировки строк/таблиц.

Стратегии:
- JSON:
  - Файловые блокировки (`portalocker`), атомарная запись (`os.replace`).
  - Версионирование файла (проверять, что не изменился с момента чтения).
- PostgreSQL:
  - Транзакции, индексы уникальности (например, на `book_id`/комбинации полей).
  - Optimistic locking (версия записи/штамп), правильный уровень изоляции.

## Маршруты API 
- POST `/books/` — создать книгу
- GET `/books/` — список книг с фильтрами (query‑параметры)
- GET `/books/{book_id}` — получить одну книгу
- PATCH `/books/` — частичное обновление по `book_id` (query)
- DELETE `/books/` — удалить по `book_id` (query)
